# MebelDocs AI — план следующих этапов

Дата фиксации: 18 июля 2026.

## Цель ближайшего цикла

Не добавлять новые крупные направления, пока существующий контур не станет пригодным для закрытого пилота.

Текущая база уже умеет:

`профиль → контрагент → заказ → счёт → PDF → подтверждение → audit log → платёж → сверка → импорт ЭСФ XML`

Следующий цикл должен превратить этот набор функций в надёжный, проверенный и доступный по HTTPS закрытый пилот.

---

## Этап A — Стабилизация локального MVP

### Результат

Один пользователь проходит полный сценарий без ручного обращения к API и без критических дефектов данных или PDF.

### Работы

1. PDF и документы
   - подключить валидный кириллический шрифт через `@pdf-lib/fontkit`;
   - проверить длинные русские и казахские строки;
   - проверить переносы, таблицу, итоги и формат A4;
   - добавить визуальные fixtures;
   - подтвердить отсутствие повреждённых или обрезанных PDF.

2. Профиль и контрагенты
   - закончить редактирование профиля компании;
   - добавить список, создание и редактирование контрагентов;
   - исключить тихое изменение snapshot подтверждённого документа;
   - показывать источник и статус подтверждения данных.

3. Платежи
   - добавить пользовательский список платежей;
   - добавить экран ручного сопоставления со счётом;
   - показать оплачено, остаток и историю сопоставлений;
   - проверить частичные платежи;
   - проверить несколько платежей на один счёт;
   - проверить сторнирование и повторную команду.

4. ЭСФ XML
   - добавить UI загрузки XML;
   - показать найденные поля и расхождения;
   - разделить baseline confirmation и final check;
   - защититься от повторного импорта;
   - добавить понятные ошибки повреждённого или неподдерживаемого XML.

5. Полный smoke-сценарий
   - профиль;
   - контрагент;
   - заказ с несколькими позициями;
   - счёт;
   - PDF;
   - подтверждение;
   - один полный и один частичный платёж;
   - импорт ЭСФ;
   - история audit events.

### Gate выхода

- `npm run lint` проходит;
- `npm run test` проходит;
- `npm run build` проходит;
- PDF визуально проверен;
- UI покрывает критические операции;
- реальные данные не попали в Git;
- нет внешней отправки;
- все необратимые действия требуют подтверждения.

## Этап B — CI и эксплуатационная надёжность

### Результат

Каждое изменение автоматически проверяется до попадания в `main`.

### Работы

- добавить GitHub Actions workflow;
- выполнять `npm ci`, typecheck, tests и production build;
- добавить secret scanning и проверку запрещённых путей;
- публиковать test summary;
- запретить merge при красных проверках;
- добавить минимальные integration fixtures без реальных данных;
- зафиксировать rollback и troubleshooting;
- проверить dependency audit.

### Gate выхода

- status checks отображаются на каждом PR;
- намеренно сломанный тест блокирует merge;
- секрет или файл из `data/raw` блокируется;
- чистая ветка проходит все проверки повторяемо.

## Этап C — Storage migration и Cloudflare preview

### Результат

Приложение работает по HTTPS в preview и не использует локальный `node:fs` как runtime storage.

### Работы

1. Runtime
   - подключить OpenNext adapter;
   - добавить Wrangler;
   - создать preview environment;
   - проверить compatibility через `workerd`.

2. Данные
   - выбрать D1 или PostgreSQL для прикладных сущностей;
   - реализовать облачные repository adapters;
   - сохранить доменные interfaces;
   - подготовить миграции;
   - перенести append-only audit log.

3. Файлы
   - создать private R2 bucket;
   - хранить XML, PDF и импортированные файлы приватно;
   - выдавать короткоживущий доступ;
   - ограничить CORS и размеры файлов.

4. Секреты и доступ
   - использовать Workers Secrets;
   - исключить секреты из client bundle;
   - создать одного пилотного пользователя;
   - разделить read и write access;
   - добавить базовый rate limiting.

5. Эксплуатация
   - backup/restore;
   - structured logs;
   - alerting;
   - rollback;
   - custom domain после стабильного preview.

### Gate выхода

- preview работает без локального диска;
- все critical flows проходят на демо-данных;
- backup восстановлен в тестовой среде;
- файлы нельзя получить без разрешения;
- логи не содержат документов, реквизитов и секретов;
- security/privacy review завершён.

## Этап D — Закрытый пилот ИП «Гранд Мебель»

### Результат

Ограниченный реальный сценарий используется владельцем под ручным контролем.

### Порядок

1. Сначала только демо-данные.
2. Затем один обезличенный исторический кейс.
3. Затем ограниченный реальный кейс без внешней отправки.
4. Все документы проверяются вручную.
5. Ошибки и исправления записываются.
6. Автоматическая отправка, ЭЦП и ИС ЭСФ остаются выключенными.

### Метрики

- доля успешно завершённых сценариев;
- число ручных исправлений;
- ошибки сумм и статусов;
- ошибки PDF;
- ошибки сопоставления платежей;
- расхождения ЭСФ;
- время на один документ;
- причины остановки сценария.

### Gate выхода

- минимум 20 контролируемых операций;
- нет потери документов и audit events;
- нет неконтролируемых внешних действий;
- критические ошибки устранены;
- сформирован отчёт пилота.

## Этап E — Закрывающие документы

### Результат

Счёт превращается в продажу и закрывающие документы без повторного ввода строк.

### Работы

- сущность продажи/реализации;
- З-2;
- Р-1;
- разделение смешанного заказа на товар и услугу;
- договор и доверенность как отдельные признаки;
- version snapshots;
- связи `счёт → продажа → З-2/Р-1 → ЭСФ → платёж`;
- статусы, отмена и исправление.

Не начинать до успешного закрытого пилота основного контура.

---

## Этап F — AI-приёмщик в теневом режиме

### Результат

ИИ формирует проект операции, но не выполняет её самостоятельно.

### Работы

- структурированный разбор текста;
- confidence по полям;
- цитирование источника;
- обязательное подтверждение;
- журнал исправлений;
- 30 теневых операций;
- отчёт точности;
- голосовой ввод после стабильного текста.

ИИ не рассчитывает деньги, не назначает статусы и не отправляет документы.

### Результат

## Этап I — ЭЦП и ИС ЭСФ

Начинать только после отдельного юридического и технического аудита.

- актуальный SDK;
- NCALayer;
- отсутствие хранения пароля ЭЦП;
- подписание владельцем;
- статусы и регистрационные номера;
- исправленные и дополнительные ЭСФ;
- отказоустойчивость.

## Отдельный трек — SketchUp MCP

SketchUp MCP не блокирует MebelDocs AI и развивается отдельным модулем после закрытого облачного пилота.

Порядок:

1. локальный Windows Worker;
2. Ruby extension;
3. безопасный MCP bridge;
4. очередь задач;
5. сохранение SKP/PNG/спецификации;
6. отдельный GPU cloud pilot;
7. интеграция только через стабильный контракт.
